# 14.4.9 — refresh and shared-decision restoration

Restore captured UP, DOWN and SIT_OUT Calls by canonical epoch window identity,
not a formatted clock label. Refresh, wake and manual restore use one adopter.
The original direction, capture time, score, reason, blocker and ticker survive
warmup and a refresh after the cutoff. Restoring an existing Call is not approval
for a new late Call. Engine-only locks and forming candidates remain distinct.

Keep a bounded local captured-decision cache and consult captured canonical log
rows. If the shared slot is missing on a fresh device, strictly read the cloud
Call ledger once for that window before creating a replacement. Only actual
captured-at-lock originals qualify; historical amended rows are not invented
captures. Rehydrate scoped engine time-series/release history without treating
an engine lock as a committed Tara Call. Alert on a conflicting displayed
direction corrected to the earlier canonical capture; do not resend old alerts.

Rollover clears local state, not the shared cloud document. Renew the watcher
each actual window; cancel obsolete subscriptions and async results. A newer
realtime/manual/wake response defeats a delayed initial/history read. Failed
reads remain pending and retry with an explicit restoration error; they are not
interpreted as an empty shared slot. Successful restoration clears that transient
error so it cannot become the next sit-out's captured reason.

Conditional publication reads the latest server row, preserves the canonical
captured winner, and updates only the matching row timestamp/revision. Absent
rows use conflict-ignore insertion. Conflicts re-read and retry, without a blind
upsert fallback. Formation, null, stale-window and delayed queued writes cannot
erase a committed Call. Recheck window identity after the awaited server read.
Throttle formation backup to ten seconds, not the decision loop; committed Calls
and new engine locks still request publication immediately. No database schema,
credential, order endpoint or access-policy change is required.

Tests run the actual app restoration/lifecycle functions and effect callbacks,
not only the comparator. They cover both directions and sit-outs; warmup and
past-cutoff refresh; cache failure; missing-slot captured ledger recovery;
read errors/retries; wake, manual and realtime races; rollover; original capture
preservation; scoped engine-only restoration; conditional concurrent publishers;
and in-flight reads spanning a boundary. A fake server exercises the actual
installed Supabase SDK's JSON filters, conditional PATCH and conflict-ignore
insertion. It does not write production data or launch a trading engine.

Keep the 420-second 15m cutoff, existing confidence thresholds, tier/sample
ladder, directional gap/signal gates, price band, abort/cooldown rules, hourly
decision rules and AutoTrade settings/entry/exit/order logic unchanged. Maintain
live-execution pause. Tests and deployment prove the scoped repair, not improved
prediction quality, profitability, or a lock in every window.

Older running browser bundles do not hot-swap. Refresh is user-controlled;
an original Call legitimately retains its capture's older modelVersion after
loading a newer app. An old client can still perform its old blind write/delete
behavior; this client-side release is not a server-enforced global writer fence.
No existing production record is manually edited or backfilled by this release.

Rollback by reverting this release if original captures change, restore stalls,
scope-conflicting decisions appear, conditional writes fail, or rendering breaks.
Keep execution paused during rollback. Verify running-version and future-window
runtime behavior separately from served-bundle and isolated-test verification.
